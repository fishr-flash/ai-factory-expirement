# Платформа: проверенные возможности, неизвестное и план проверки

**Срез документации:** 18.10.2026. Документация провайдера меняется; перед реализацией и перед выпуском перепроверить ссылки, версии SDK/API, статус beta/GA, лимиты, цены и доступность в аккаунте. «Проверено» ниже означает, что поведение описано в публичных официальных документах, а не что оно проверено в production-аккаунте AI Factory.

## 1. Рекомендуемая опорная платформа

OpenAI Agents API описан как управляемый Codex harness с сессиями, событиями, sandbox, вызовами инструментов и мультиагентным делегированием. OpenAI-hosted sandbox исполняет команды в рабочей среде и имеет настраиваемый сетевой доступ. Сессии можно продолжать новыми сообщениями; работы/turns и usage можно считывать API. Эти свойства подходят для целевого runtime, если отдельные прототипы ниже подтвердят конкретную конфигурацию и аккаунт.

Публичное руководство Agents API по multi-agent описывает `multi_agent.enabled`, создание/ожидание/остановку подагентов, предел параллелизма, общую файловую среду с координатором и подагентами, а также наблюдаемые события. В документации отдельно сказано, что подагенты наследуют инструменты и не поддерживают function tools. Руководство не даёт достаточного подтверждения, что нужные нам роли, отдельные модели/настройки для разных уровней и вложенная схема Chief→Planner→Worker доступны именно в Agents API без оговорок. Поэтому A-03 и P-018 остаются обязательной проверкой; нельзя замаскировать её конфигурационными предположениями.

## 2. Матрица возможностей и решения

| Возможность | Статус по документации | Проектный путь | Что остаётся проверить |
|---|---|---|---|
| Облачный runtime без пользовательского компьютера | **Проверено:** OpenAI-hosted sandbox управляется OpenAI; приложение создаёт сессию и получает события. | Agents API + hosted sandbox. | Доступность в целевом аккаунте/регионе, quotas, конкретные размеры и стоимость. |
| Сессия и восстановление между ходами | **Проверено:** сессии хранят конфигурацию/историю/работу и принимают follow-up сообщения. Среда отдельна и имеет срок жизни. | Continue существующей сессии, если доступна; иначе новый session из Git checkpoint. | Реальное восстановление после закрытия клиента, превышения окна/квоты, сбоя sandbox и длительного ожидания. |
| Создание подагентов | **Проверено в документации:** включается через multi-agent; есть create/message/wait/interrupt и concurrency. | PO динамически включает delegation по решению о структуре. | Выполнить минимальную сессию с coordinator и 2 подагентами на target project. |
| Несколько управленческих уровней | **Не подтверждено достаточно:** руководство описывает подагентов в сессии, но не гарантирует конкретную вложенную организацию PO→Chief→Planner→Worker. | Иерархические роли и назначения хранятся в Git; для вложенных управленческих сессий потенциально использовать отдельные сессии. | Прототип с вложенным делегированием, ID parent/child, отдельными ролями и принятой работой; если нельзя — design blocker A-03/A-04. |
| Разные модели по роли/задаче | **Частично подтверждено:** у агента/сессии есть `model` и `reasoning`; multi-agent guide не доказывает, что модель настраивается для каждого subagent отдельно. | Реестр доступных моделей; проверенный model policy; при необходимости отдельная Agents API сессия для отдельной роли. | Подтвердить per-subagent model/effort или рабочую схему независимых сессий. Логировать фактически использованную модель из API trace. |
| GitHub read/write в двух репозиториях | **Возможно средствами среды/инструментов**, но выбранная политика аутентификации и Git push не подтверждена этой архитектурой. API vault умеет выдавать HTTPS credentials к разрешённым host, однако это ещё не проверка git CLI в нашем сценарии. | Временный GitHub App token, отдельные права по репозиториям, ветки на run, vault proxy если подходит. | Прототип клонирования и push в две тестовые репы; подтвердить GitHub App token, API/HTTPS host allowlist, отказ push в защищённую ветку и отсутствие секрета в истории/трассах. |
| Чтение и запись файлов | **Проверено:** hosted sandbox имеет workspace и Files API; опубликованные artifacts — immutable copies. | git clone/push — основная запись; sandbox artifacts только для диагностических экспортов. | Проверить доступные лимиты/путь восстановления и не считать `/workspace/outputs` рабочей Git-репой. |
| Учёт model token usage | **Проверено как best-effort:** root/subagent turns могут содержать usage, который бывает `null` или уточняется позже; это не итоговый счёт. | Ledger хранит наблюдения с временем, источник, неизвестное отдельно. | Получить фактические поля usage для каждого agent/turn и сверить с dashboard/billing sample. |
| Квоты и денежные лимиты | **Частично:** публичные rate limits и API spend limits документированы; непрозрачные плановые/подписочные лимиты в этой схеме не считаются доступными API. | Запрашивать текущий доступный budget вручную/по поддерживаемому API; жёсткий лимит фабрики — внутренний stop, не гарантия отказа провайдера. | Проверить 429, платёжное ограничение, reset headers/semantics, раздельную тарификацию sandbox/model и отсутствие доступа к billing API. |
| Остановка и отмена | События/API lifecycle описаны, но тонкости отмены дочерних задач и безопасного состояния файлов нужно подтвердить. | Manager stop + API interrupt/cancel по поддерживаемому механизму; сохранять Git checkpoint до остановки, если возможно. | Проверить остановку root/subagents и неуспешные/частичные push. |
| Webhook / автоматический wake | API webhooks описаны для событий, но это не доказывает автоматическое пробуждение по сбросу любой квоты. | В v1.0 ручное/явное resume; webhook лишь для доставки поддерживаемых событий. | A-06 требует последующую авторизованную сессию; автоматическое пробуждение не входит в критерии, если платформа не подтверждает его. |
| Сессии и sandbox по срокам | **Проверено с оговоркой:** sandbox удаляется после периода неактивности; артефакты сохраняются, сессия хранит turn state. | Git checkpoint до длительного ожидания; не рассчитывать на временные файлы sandbox. | Проверить фактические TTL/очистку, удаление сессии и опубликованных artifacts на выбранном аккаунте. |
| Только файлы GitHub для аудита | Провайдер даёт Dashboard/API traces, но требование A-14 должно выполняться без них. | Все обязательные run decisions, IDs, модели/prompt versions, commits и status — в двух Git repos. | Сценарий закрывает доступ к dashboard и восстанавливает/аудирует запуск только из репозиториев. |
| Затраты на hosted sandbox | Документация разделяет тарификацию модели и sandbox. | Два отдельных cost item; пока данные не получены, unknown/estimate. | Проверить актуальные цены и детализацию биллинга, сохранить дату/ссылку. |

## 3. Критические неизвестные и blockers

### B-01 — Иерархические роли и выбор модели

Официальные примеры Agents API подтверждают root coordinator и subagents, но не подтверждают, что вложенный менеджер может создавать собственного Worker с независимой моделью/уровнем рассуждения. Также подагенты не поддерживают function tools. Нужно решить прототипом:

1. Создать run root PO и отдельную иерархию на 3 уровня.
2. Создать 2 Planner-ветки и Worker-задачи, включая минимум одного вложенного Child.
3. Для каждой роли передать разные инструкции; для моделей — проверить, что выбранная/использованная модель действительно отличается и доступна в trace.
4. Сверить usage и связи parent/child по сессиям/turns и Git manifest.
5. Если Agents API не позволяет это в одной сессии, испытать отдельные role sessions с Git-контрактом и короткоживущим workflow dispatcher. Такой dispatcher должен оставаться stateless, без собственной базы и без постоянного сервера. Если это требует обязательного специализированного hosted service, представить это заказчику как blocker против P-044, не переименовывать в необязательный модуль.

### B-02 — Доступ к двум репозиториям из sandbox

В тестовой GitHub организации создать фабричную и продуктовую репозитории с защитой default branch. Прототип должен использовать только короткоживущую установку GitHub App, читать обе репы, записывать каждую в отдельную ветку, пройти неавторизованный доступ/403, конфликт fast-forward и секретное сканирование git config/history. Нельзя продолжать с PAT пользователя с широкими правами, если App token не сработал.

### B-03 — Хранение и resume

Запустить долгую task, сохранить checkpoint в Git, оборвать клиентскую подписку, затем восстановить session events/items и продолжить. Отдельно удалить/дождаться expiry sandbox и создать новую сессию, восстановив только из git commits. Пройти A-06 без двойного запуска и проверить реальный lifetime API session в аккаунте.

### B-04 — Квоты и фактическое потребление

Провести квотно-ограниченный запуск с двумя задачами и резервами. Получить usage per root/subagent и несколько классов 429; записать reset semantics, unknowns и стоимость без предположений. Перепроверить тариф API и sandbox независимо от подписок ChatGPT/Codex.

### B-05 — Инициатор без постоянного backend

Проверить ручной запуск из имеющегося интерфейса либо stateless hosted workflow: create, stream/inspect, required action, запись checkpoint, exit и последующий resume. Если продолжение требует постоянно работающего endpoint, протоколировать архитектурное противоречие и оценить serverless/ручной вариант. Не включать автопробуждение после quota reset как неявную зависимость.

## 4. Обязательный отчёт о проверке платформы

Перед реализацией и повторно перед v1.0 оформить `platform-verification.md` с:

- датой, аккаунтом/проектом и API/SDK версиями (без секретов);
- точным request shape и результатом для каждого теста;
- поддержанными моделями и полями конфигурации роли;
- доказательством GitHub repo/ref scope и отсутствия credential leakage;
- наблюдаемыми типами событий, способами восстановления и временем жизни;
- фактическим полем usage и сравнением с доступным billing evidence;
- ограничениями, fallback, открытыми blockers и решением заказчика.

Ни один blocker нельзя закрыть словом «должно работать» или публичным примером, не выполненным в целевой конфигурации.
