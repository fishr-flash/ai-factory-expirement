# Отчёт о верификации проектных предпосылок

**Дата исследования:** 18 октября 2026 г.  
**Объект:** проектная документация AI Factory v1.0.  
**Уровень проверки:** изучение официальной документации и проверка покрытия требований документами. Реализация и эксплуатационные сценарии не запускались; это отчёт для design review, а не отчёт о готовности продукта.

## 1. Результат

Рекомендованная базовая архитектура — OpenAI Agents API, OpenAI-hosted sandbox и два независимых GitHub-репозитория с GitHub как долговременным источником истины. Публичные документы подтверждают наличие управляемых сессий, follow-up/continue, hosted sandbox, multi-agent delegation, наблюдения turns/subagent ID и best-effort token usage. Эти факты достаточны для выбора кандидата на прототип, но сами по себе не доказывают, что система способна удовлетворить обязательные сценарии в нужном аккаунте.

## 2. Трассируемость документов

Таблица в [`traceability.md`](traceability.md) содержит 48 строк P-001–P-048 и 15 строк A-01–A-15. Проверено по текущему файлу, что каждая нумерованная спецификация имеет отдельную строку сопоставления. Документы покрывают архитектуру и альтернативы, роли/полномочия, state machines, межрепозиторные операции, контрактные структуры, ошибки и восстановление, безопасность, платформенные зависимости, план валидации и оценки реализации.

## 3. Открытые blockers и ограничения доказательств

До начала реализации требуется закрыть или формально вынести на решение:

1. **B-01:** подтвердить иерархические управленческие роли и конфигурацию модели/effort для каждого нужного уровня. Публичная документация не заменяет сквозной прототип.
2. **B-02:** доказать изоляцию доступа к двум репозиториям GitHub и защиту секрета в реальном способе clone/push.
3. **B-03:** доказать восстановление сессии и восстановление после потери sandbox из Git checkpoints.
4. **B-04:** измерить квоты/usage и обозначить ограничения, которые нельзя enforce на стороне провайдера.
5. **B-05:** подтвердить путь запуска/продолжения без локального компьютера и без постоянного собственного сервера.
6. Человек-заказчик должен принять решения из [`architecture.md` §6](architecture.md#6-требует-одобрения-человека): аккаунт/оплата, данные и хранение, trigger, merge policy и budget/approval границы.

Поскольку текущая комиссия ограничена документацией и запрещает реализацию, runtime проверки оставлены планом. Они не должны ошибочно читаться как пройденные. Каждая из них обязательна перед завершением релиза 1.0; препятствие платформы фиксируется как blocker релиза, а не как изменение требований.

## 4. Готовность к рассмотрению

Документация пригодна для независимого review без исходного чата: исходная спецификация доступна в репозитории, термины объяснены в design index, решения и открытые вопросы выписаны, а утверждения о провайдере сопровождаются официальными ссылками и пределом доказательства. Статус реализации — **не начата**; статус платформенных сквозных проверок — **не выполнены**.
